# 🌊 digiwallsys — v1.8.0

> *Name: Estuary*

**Status:** Release (code-complete; pending production deploy + migration + integration testing against a real database)

---

## 📖 Overview

**Estuary** adds the two financial features deliberately set aside from Convoy:
multi-currency wallets with self-service conversion, and shared/family wallets
with per-member spending limits. Both touch core ledger and wallet-resolution
logic directly, so they get their own dedicated migration and testing pass
instead of being bundled into a lower-risk release.

## 🎯 Objectives

- Let a user hold more than one currency wallet and convert between their own
  wallets without weakening the existing balanced-journal invariant.
- Let a wallet be shared with other users (e.g. a family), each with an optional
  monthly spending limit, without changing behavior for anyone who isn't using it.
- Keep every existing money-movement code path — direct sends, payment requests,
  scheduled transfers — behaviorally identical when the new capabilities aren't in use.

## ✨ Scope

### 💱 Multi-currency wallets

- `wallet` now allows one row per `(userid, currency)` instead of exactly one
  wallet per user.
- Conversion between a user's own wallets is posted as two independently-balanced
  same-currency journals against a system FX suspense account, rather than a
  single cross-currency journal — `postJournal()`'s existing balance check
  compares raw amounts and is intentionally left untouched, since a cross-currency
  journal cannot balance in raw units without weakening that check for every
  existing caller.
- `fx_rates`: an append-only rate history (never mutated in place) so a past
  conversion stays auditable against the rate actually in effect at the time.

### 👨‍👩‍👧 Shared / family wallets

- `wallet_members`: authorizes a user other than the wallet owner to send from
  it, with an optional monthly `spending_limit`. Every existing wallet is
  backfilled with its owner as the sole member, so nothing changes until someone
  is explicitly added.
- `transactions.spender_userid` records which member actually initiated a
  transfer from a shared wallet, distinct from the wallet's owner, so per-member
  spending limits can be enforced and audited.

## 🏛️ Architecture Progress

The riskiest change is `transferService.executeTransfer`'s wallet-resolution
query, generalized to accept an explicit currency and an optional delegated
owner — every existing caller (`sendMoney`, payment-request acceptance, the
schedule worker) keeps its exact prior behavior by omitting the new parameters.

## 💻 Compatibility

iOS · Android · Web · requires running `config/migrations/004_estuary_features.sql`
against the target database before deploying this version's API.

## 🏁 Release summary

Estuary is code-complete and passes the existing backend unit-level test suite,
but the PostgreSQL integration suite could not run in the environment this was
built in (`TEST_DATABASE_URL` not configured) and it has not been deployed or
migrated against a production database. Run that integration suite for real
before deploying.
